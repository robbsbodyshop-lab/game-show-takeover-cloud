## 3. Focus areas

### 3.1 Hidden information (P-002, FR-014)

Verified clean:

- Stage components receive `audienceView` only. Feud: `FeudController.buildView()` (`FeudController.ts:1608-1620`) returns `audience: audienceView(...)`; `hostView` appears only in `hostData()` (host surfaces). Wheel: `buildSnapshot()` uses `audienceView(this.display)` (`WheelController.ts:1365`); `hostView` only in `games/wheel/hostData.ts:9,210`.
- Leak tests exist at three levels: selector JSON (`feud/selectors.test.ts:82-139`, `wheel/rules.solving.test.ts:148`, `rules.bonus.test.ts:120`), controller view model (`FeudController.test.ts:855-860`) and rendered DOM (`FeudGame.test.tsx:51-59`, `WheelGame.test.tsx:42-74,140`).
- `audience` realtime payload (`schemas.ts:72-78`, built in `StageSession.tsx:91-98`): `phase`, `paused`, per-team `score` only. The optional `clock` is never populated. The schema has no field that could carry an answer, puzzle or envelope.
- `controls` payload (`schemas.ts:54-63`; Wheel `phoneControls` `selectors.ts:320-358`; Feud `FeudController.ts:1248,1281`): booleans, a team name and fixed label strings. No puzzle or survey text.
- `teams` is `{id, name, color}`; `join_room` returns the same three fields extracted from `event_state` (`0001_init.sql:421-433`), never the whole state.
- The host snapshot is published only on the `host` topic (`hostChannel.ts:113`), limited by RLS to the owner's sessions (`0001_init.sql:639-671`); phones do not join it (`roles.ts:12-16`). The `BroadcastChannel('gst-host')` mirror is same-origin, same-browser.
- Residual, by design: the F2 drawer renders hidden data inside the stage window; Show mode and closing the drawer remove it.

The 11 events and their senders (`SENDER_OF`, `schemas.ts:219-231`) agree with the design table; the `from` literal in each schema rejects a wrong-sender message on receipt. `private: true` is set on every channel (`SupabaseRoomTransport.ts:208`); `realtime.setAuth` is re-sent on `TOKEN_REFRESHED`/`SIGNED_IN` (`:342-347`). What the policies cannot see is the `team` field inside a payload (F1).

### 3.3 Engine purity

`src/engines/**` and `src/judging/**` import no React, DOM, Supabase or `@/` alias, and use no `Math.random`, `Date.now`, `localStorage`, `window`, `document`. The one non-relative import is `zod` in `engines/event/schema.ts:5`. One cross-folder import, `engines/feud/fastMoney.ts:7 -> judging/normalize`, is permitted by the design. `src/games/**` never imports `@/data` or `@/realtime`. Nothing enforces this mechanically (L8).

### 3.4 Security

- Room code: 4 letters from 20 consonants, drawn from `gen_random_uuid()` bytes in SQL (`0001_init.sql:337-341`), regex CHECK on the column; modulo bias (5.08% vs 4.69% per letter) is immaterial. 160,000 codes is the specified entropy; the guess limit is per anonymous user and resets with a new anonymous session (F9).
- Anon key: only a publishable key in `.env.local` (git-ignored) and in the bundle, as designed.
- XSS: no HTML sinks. Team names, nicknames, `ua`, typed answers, `turnName`/`offLabel` are rendered as React text. Team `color` is used only as `borderColor`/`backgroundColor` (`BuzzScreen.tsx:80`, `TeamPicker.tsx:49`). QR is drawn on a canvas. `vercel.json` has no CSP (the spec does not ask for one).
- SQL: every `security definer` function sets `search_path = ''`; `revoke all` from `public, anon, authenticated` then explicit grants; `join_attempts` has no grants.
- Stage-side trust: it checks that a team exists, not who sent the message (F1).

## 4. Findings, ranked

### Blocking

**F1. FR-025 / P-004: a phone can act as any other team, and the docs claim it cannot.** (High; the fix starts in the spec.)
Observed: the `phones` write policy checks only `m.role = 'phone'` for the room (`0001_init.sql:609-621`). `press`, `action` and `feud-answer` carry a client-chosen `team` (`schemas.ts:83-103`; sent at `src/phone/useStageLink.ts:255,276,288`), and the stage only checks that the team exists (`src/stage/phoneBridge.ts:55,76,97,107`). Broadcast carries no sender identity, so any joined phone can buzz, SOLVE with an answer, or submit a Feud answer for another team. RLS cannot read payload fields, so no test in `rls.sql` covers it. `docs/DEPLOYMENT.md:92` ("stops a phone from ... posing as another team") and `docs/ARCHITECTURE.md:231` overstate what the policies do.
Requirement: FR-025 "from acting as another team, enforced server-side (private channels + RLS), not only in the UI"; P-004.
Resolution path: decide in the spec. Either narrow FR-025 to what private channels can enforce (non-members, stage impersonation) and add a stage-side rule, or change the design to one phones topic per team (`room:CODE:phones:N`, policy joins `room_members.team`), which RLS can enforce. Then correct both docs and add a test.

**F2. FR-004 / FR-005 / US-013: cloud saves are starved by any change stream faster than 500 ms.** (Medium-high.)
Observed: `src/data/persistence.ts:224-229` re-arms a 500 ms trailing timer on every `save()` with no maximum wait. Wheel Fortune Frenzy ticks the engine every 250 ms for 30 s (`src/games/wheel/WheelController.ts:63,834-838`; `src/engines/wheel/plan.ts:8`), each tick reaches `onStateChange` (`WheelController.ts:476,506`) and then `GAME_STATE` (`src/engines/event/eventReducer.ts:364-366`). Probe V6: 0 saves in 30 s. The local cache is written, so a same-browser reload is fine, but "any device signed in as the host" resumes up to 30 s behind, and a crash mid-Frenzy loses the clock position.
Requirement: FR-004 "save it to the cloud within 2 seconds".
Fix: add a maximum wait (flush at most 2 s after the first unsaved change) and a test with a continuous stream. The spec text is right.
